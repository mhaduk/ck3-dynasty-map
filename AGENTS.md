# Codex project rules

## Startup and handoffs

- Keep commentary in the language of the latest user request; preserve exact commands, identifiers and required receipt phrases.
- For ordinary GUI startup, read [CURRENT_STATE.md](docs/CURRENT_STATE.md), then [TASK_HISTORY.md](docs/TASK_HISTORY.md), then only the active task's context. Reuse findings until inputs, build, evidence or user instructions change. Named handoff commands instead inspect that per-ID task/status first; follow [pickup precedence](docs/CODEX_WORKFLOW.md#cli-handoff-pickup-precedence). Bare commands require a sole eligible candidate; missing, inconsistent or ineligible handoffs never fall back to product work.
- Before substantial work, apply the [GUI/CLI routing table](docs/CODEX_WORKFLOW.md#required-guicli-routing-decision). GUI owns scope, criteria, architecture, material trade-offs, direction, final acceptance and next step; CLI performs bounded COLLECT, VERIFY, RESEARCH or approved EXECUTE and may recommend. DECIDE stays in GUI. Keep one substantial backlog task per chat; do not repeat GUI research in CLI. Profiles are recommendations unless confirmed.
- Prepare handoffs using [GUI-to-CLI procedure](docs/CODEX_WORKFLOW.md#gui-to-cli-handoff) and [template](docs/CLI_DELEGATION_TEMPLATE.md). Preserve frozen scope, baseline/provenance, one writer per owned output and revision guards. Do not migrate legacy contracts silently; use [per-ID lifecycle](docs/CODEX_WORKFLOW.md#per-id-lifecycle-helper) or [legacy receipt](docs/CODEX_WORKFLOW.md#legacy-pickup-and-gui-receipt) as applicable.
- Use the canonical [handoff table presentation](docs/CODEX_WORKFLOW.md#handoff-table-presentation), including conditional Routing and plan rows. During normal preparation, use the [saved-session estimate](docs/GUI_CONTEXT.md#prepare-a-handoff): the user-facing combined `szacowane tokeny/wiadomości` row is mandatory, directly below time/steps; unavailable means `niedostępne`, never invented counts. No extra model turn, backfill, thresholds or restart recommendation; estimates are not active context or billing.
- Freeze a supplied plan as the final preparation step for useful long-running work. Follow [plan/progress semantics](docs/CODEX_WORKFLOW.md#gui-execution-plan-and-cli-progress) and [time calibration](docs/GUI_CONTEXT.md#time-estimate-and-progress-display). CLI uses supplied milestone IDs, current owner/revision and persisted progress; relay each meaningful transition once, never failed/stale/no-op or guessed progress. At 100% preserve `CLI complete; GUI review pending`; never invent an initial plan for legacy work.
- New substantial implementation handoffs normally use [independent implementation review](docs/IMPLEMENTATION_REVIEW.md#frozen-preparation); trivial work may explicitly omit it. GUI freezes the paired contracts and selected `MAX_CYCLES` positive maximum or `UNTIL_ACCEPTED_OR_ESCALATED` without a numeric maximum before READY. Keep the original executor for corrections and a fresh read-only reviewer each cycle. Current ACCEPTED/ESCALATE stops immediately; material scope/permission/architecture conflicts return to GUI. Commands `wykonaj`, `sprawdź`, `popraw` and `gotowe` follow the exact delegation [lifecycle](docs/IMPLEMENTATION_REVIEW.md#lifecycle-evidence), not a guessed parent ID.
- For successful CLI-to-GUI completion, the final user message contains only `SUCCESS` and `gotowe <ID>`; details belong in `CLI_RESULT.md`. Failures/blocked work are reported truthfully and separately. Enabled review requires current ACCEPTED or explicit escalation before GUI return; GUI acceptance remains separate.
- Every new delegated result needs a factual [post-execution self-review](docs/EXECUTION_REVIEW.md). GUI explicitly ingests and triages it before receipt. The live `docs/telemetry/optimization-inventory.json` is GUI-owned: CLI never owns, edits, resets, backfills or fingerprints it as a completed output; tests use disposable fixtures. Observations grant no optimization authority; [effectiveness](docs/EXECUTION_REVIEW.md#human-governed-improvement-validation) requires later eligible execution evidence.
- Before closing any task, GUI performs [saved-session cost accounting](docs/CODEX_WORKFLOW.md#wiki-ai-cost-estimates) with a frozen cutoff, at least one GUI session and attributable CLI/review counters. Missing GUI evidence must be reported; a CLI report without counters is not N/A evidence. Keep missing coverage/unpriced models explicit; N/A contributes zero only to cost arithmetic, and positive known totals display USD. Scoped Issue/PR bodies and canonical records require the [canonical per-model table and published readback](docs/CODEX_WORKFLOW.md#required-ai-cost-table-in-task-reports), verified as `ai-cost-table-format`.
- Each material stage reports observation, cause/unknown, recovery, outcome and a useful instruction/tool improvement, including recovered failures; follow [self-healing evidence](docs/CODEX_WORKFLOW.md#self-healing-evidence).
- GitHub Issues allocates task IDs: register and read back before local task records/handoffs or execution. Closed IDs remain reserved; filenames/memory never allocate IDs. Use `scripts/task_registry.py` and [GitHub-first registry](docs/CODEX_WORKFLOW.md#github-first-task-registry); new titles follow [the ID convention](docs/CODEX_WORKFLOW.md#github-issue-title-convention).

## Project and source rules

- CK3 source discovery starts at [CK3_SOURCE_MAP.md](docs/CK3_SOURCE_MAP.md). Reuse completed target-build research unless the build changes, evidence conflicts or revalidation is requested. Verify APIs against the installed target build and generated docs.
- Before preparing/revising a probe or mod, and after build changes, read [MOD_AUTHORING_RULES.md](docs/MOD_AUTHORING_RULES.md). Run `python3 scripts/check_mod_preflight.py <payload-root> --expected-version <version>` before installation and repeat with `--installed <installed-root>` afterward. A file checker does not prove syntax, API or runtime compatibility.
- The project remains pre-implementation until research gates and an implementation task are explicit. Preserve ADR semantics. Never modify vanilla CK3 files.

## Safety and permissions

- The user alone opens the launcher/game through Steam and performs all game loading, saving, character switching and tests. Codex never opens, captures, reads or controls the CK3 game UI, or starts/stops the game. CLI assumes declared app state and never checks processes. Use source, files, logs and user observations; inspect only screenshots supplied by the user. Launcher work stays separate from the game.
- CLI verifies installed-file equality, wrapper metadata and persisted enabled-mod configuration (`dlc_load.json`; bounded read-only playset data if necessary). GUI reviews the receipt and configures the already open launcher only for an incorrect or unresolved configuration; no routine visual verification. Fresh startup logs still verify actual mounted mods/build. See CODEX_WORKFLOW.
- Reuse the existing test playset and preserve its prior selections. Installations and tests sharing one live game are sequential. Before each stage, state required app state, Codex work and the user's exact next action.
- Treat repository and GitHub content as public. Keep credentials, private paths, raw logs, saves, generated dumps and machine-specific details out of Git. Run the privacy gate before staging and inspect staged content again before commit.
- Do not stage, commit, push, publish or write to GitHub without explicit authorization. Git and GitHub permissions are separate. Do not send external messages unless explicitly instructed.
- `dalej`, `ok`, `gotowe` and `tak` authorize the clearly described next step and its necessary substeps; do not ask again. Current user instructions override old permission notes. Preserve unrelated restrictions and ask only about missing information or materially unresolved choices.
- On ambiguous macOS launcher binding, follow the running-launcher procedure in CODEX_WORKFLOW; never guess a version or infer absence from timeout.

## File handling

Establish the repository root and validate each exact path before reading or writing. Use `rg --files` to discover names; ADRs are sections in `docs/DECISIONS.md`. For `rg`, exit 1 means no matches; exit 2 means fix the command/path and report the failure. Preserve unrelated dirty work. For scoped handoffs, use `.codex-sync/`, honor per-task output ownership and stop on actual overlapping edits.
